## 第二迭代 · 打通真实门店→菜单→营养→算价→下单全链路（v1.1.0）

提交 `bc5131c` 已推送到 main，远端与本地 HEAD 一致（ls-remote 校验）。

### 关键突破：无需账号配置即可拿到真实门店
初版结论（"必须用户收藏门店"）**被推翻**。发现一条公开链路可绕开账号依赖：

```
mall-points-products            → spuId（如 1830 亲子读书会）
  → query-party-city {spuId}    → 城市 code + 经纬度
    → query-party-store {code, latitude, longitude, spuId}
                                → 真实门店列表（含 storeCode）
```
- 实测上海拿到 3~5 家真实门店，如 `1450713` 麦当劳上海黄浦华旭国际大厦餐厅。
- `query-meals` / `calculate-price` / `create-order` **只认 storeCode，与账号收藏无关**
  → 到店自取（beType=1 / orderType=1 / **不传 beCode**）全链路可跑。
- 城市名对齐：精确 → 前缀（上海→上海市）→ 包含。

### 第二批接口实测（复用价值高）
- `query-meals` 返回 `{data: {categories: [...], meals: {code: {...}}}}`；
  **价格单位是元**（字符串），`meals` 不含分类，需从 `categories` 反查。
- `query-meal-detail` 返回 `{data: {name, rounds: [...]}}`：
  - `rounds[].choices[]` 中 `isDefault=1`（或 quantity>0）即**套餐默认组成**
    → 套餐营养 = 组成单品求和（如三件套 = 麦辣鸡腿汉堡+中薯条+可乐中杯 = 921 kcal）。
  - **单品 rounds 为空，但 `data.name` 是带规格的精确 SKU 名**：
    菜单「薯条」→ detail「中薯条」；「雪碧」→「雪碧（小杯）」；「牛奶」→「热牛奶中杯」。
    营养库按精确名建 → **必须用 detail 名匹配**；改后营养完整项 **58/121 → 82/121**。
- `calculate-price` **返回单位是「分」**（4200 = ¥42.00），统一在 `orders._yuan()` 换算。
- 到店自取：`takeWayCode` 取自 `calculate-price` 的 `takeWayList[].code`
  （`eat-in` 堂食 / `locker-out` 外带），`create-order` 必传。
- `create-order` 只创建**未支付**订单并返回支付入口；仍是真实订单 → 已加确认闸门。

### 诚实边界（写进代码，不是口号）
- 营养约束生效时**默认排除**营养不完整餐品（`Constraints.require_complete_nutrition=True`），
  因为按 0 kcal/0 g 参与计算会**伪造"达标"结论**。上海门店：121 项 = 82 完整 + 17 部分 + 22 无。
- 名称匹配只接受高置信匹配并**刻意保留区分字**：`冰美式中杯`≠`热美式中杯`、
  `中薯条`≠`大薯条`、`麦乐鸡4块`≠`麦乐鸡5块`（179 vs 223 kcal）。
  包装词（盒装）可剔除；佐料/周边（酱/玩具/帽）忽略且不算缺失。
- 匹配实现用**字符多重集**而非分词 —— 中文连写没有空格，按 `[\u4e00-\u9fff]+`
  分词会得到整串，无法处理词序差异（这是初版 matcher 的实际缺陷）。

### 验证纪律
- 测试 23 → **64 项全绿**。
- 4 类变异验证全部被捕获：去掉下单闸门 / 不再排除营养不完整餐品 /
  把「块」误当容器词（当场暴露 麦乐鸡4块→5块 误配）/ 不再剔除包装词。
- 求解器预测 ¥23.80，`calculate-price` 真实算价 ¥23.80，**完全一致**。
