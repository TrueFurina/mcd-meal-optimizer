# 麦当劳怎么点最划算又够蛋白？我写了个「算盘」，把这事算清楚了

> 项目：**麦麦算盘 · mcd-meal-optimizer**  
> 仓库：<https://github.com/TrueFurina/mcd-meal-optimizer>

---

## 一、起因：一个没人认真算过的问题

减脂期想吃麦当劳，脑子里会转三个问题：

1. 这顿**多少卡**？
2. **蛋白够不够**？
3. 这么点，**贵不贵**？

这三个问题看起来简单，但组合起来没人认真算过。原因很实在：

- 套餐的**营养数据是不公开的** —— 菜单上只有单品，「三件套」到底多少卡，得自己拆；
- 优惠券规则**不是一句话能说清**的 —— 满减、固定价、折扣、买一送一，混着用；
- 最后到手多少钱，**要下单才算得准**。

于是大多数人只能"感觉还行"。我做了一个工具，让这三个问题都有**确定的、可复现的答案**。

---

## 二、它是什么

一句话：**在预算内吃够营养，在营养达标时花得最少。**

输入「热量区间 + 蛋白质下限 + 预算上限」，输出**到手价最低且营养达标**的餐搭组合。

```bash
$ python -m mcd_meal_optimizer plan --store-code 1450713 \
      --kcal-min 550 --kcal-max 800 --protein 30 --budget 40 --max-items 3 --price-check

数据来源: 菜单=live:1450713 | 券=8 | 营养完整=82/121

## 方案 1 — 到手 ¥23.80（原价 ¥23.80）
- 营养: 656 kcal / 蛋白 42.0 g（目标 550-800 kcal, 蛋白 ≥ 30 g）
- 蘸酱麦麦脆汁鸡 ¥11.90
- 蘸酱炸鸡 ¥11.90

--- 真实算价 (calculate-price) ---
- **合计 ¥23.80**
```

注意最后两行：**求解器预测 ¥23.80，接口真实算价也是 ¥23.80**。这不是估算，是逐分吻合。

## 三、关键设计：不是"推荐"，是"求解"

官方报名示例给的方向是「麦当劳营养膳食专家 —— 根据每日消耗搭配麦麦套餐」。方向没错，  
但"搭配"这件事如果只是**让模型挑一个**，挑得对不对就没法验证 —— 热量记错一点、  
价格过时一点、券忘了算，你看不出来。

我选的位置是**约束优化**：

- 决策变量：点哪几样、各点几份；
- 约束：热量区间 + 蛋白下限 + 预算上限 + 件数上限；
- 目标：到手价最低（也可切"蛋白最高""每元蛋白最高"）。

解法是**动态规划**：

```
state = (热量桶, 蛋白桶, 必需掩码)
value = 最低到手价（已计入券后价）
```

为什么值得这样做？因为**它可以被证明是对的** —— 求解器是纯函数、不碰网络，  
我能拿穷举在 120 组随机小规模实例上逐一比对，DP 结果必须和穷举**完全一致**。

## 四、四个真实的坑（这部分最值钱）

### 坑 1：同一个"价格"，两个单位

`query-meals` 返回的价格是**元**，`calculate-price` 返回的是**分**。  
`price: 4200` 是 ¥42.00，不是 ¥4200。混用一次就差 100 倍。

更坑的是，`create-order` 的返回体**又回到元了**。

### 坑 2：套餐根本没有营养数据

营养库里只有单品：中薯条、麦辣鸡腿汉堡、可乐中杯各自独立。  
那"麦辣鸡腿汉堡三件套"怎么算？

答案在 `query-meal-detail` 里 —— `rounds[].choices[]` 中 `isDefault=1` 的那一项  
就是**套餐的默认组成**：

```
麦辣鸡腿汉堡三件套
  ├─ 麦辣鸡腿汉堡
  ├─ 中薯条
  └─ 可乐中杯        → 三者营养求和 = 921 kcal / 蛋白 28.0 g
```

### 坑 3：菜单上的名字和营养库对不上

菜单显示「薯条」，`query-meal-detail` 返回的&#x662F;**「中薯条」**；  
菜单「雪碧」→ 详情「雪碧（小杯）」；菜单「牛奶」→ 详情「热牛奶中杯」。

营养库是按**精确规格名**建的。用菜单名去匹配，所有带规格的单品全部落空。

改成用详情里的精确名匹配后，营养完整项从 **58/121 提升到 82/121**。

### 坑 4：新账号什么都查不到

`query-nearby-stores` 依赖账号侧已配置定位或收藏门店，**全新账号必然返回空**。  
我一开始以为"必须先去 App 收藏一家店"，后来发现有一条公开链路可以绕开：

```
mall-points-products  →  spuId
  → query-party-city {spuId}            → 城市 code + 经纬度
    → query-party-store {...}           → 真实门店列表（含 storeCode）
```

拿到 `storeCode` 之后，菜单、算价、下单**只认门店编码，跟账号收藏毫无关系**。  
所以这个工具**零配置**就能跑通全链路。

## 五、两条我划的红线

### 红线 1：缺营养的餐品，一律排除，绝不按 0 算

营养库收录 158 款，门店在售 121 项，**两者不是一一对应**。当季新品（比如龙焰系列）、  
带规格的歧义项都可能对不上 —— 上海这家店是 `82 完整 + 17 部分 + 22 无`。

如果把缺数据的餐品按 **0 kcal / 0 g 蛋白**参与计算，优化器会得出一个漂亮的结论：  
"这单完全达标"。**但那是假的。**

所以现在的做法是：**排除出解**，并在输出里如实说明有多少项被排除。  
宁可少给一个方案，也不给一个错的。

### 红线 2：下单默认只预览，必须显式确认

`create-order` 会创建**真实订单**（虽然只是未支付的）。钱的事我不自己拍板：

- CLI 层：不加 `--confirm` 只算价，不建单；
- 代码层：未确认时 `submit()` **直接抛异常，且不发出任何请求** —— 这条有测试守着。

为了确认接口契约，我在真实门店上完整跑过一次**建单 → 撤单**闭环：

```
create-order  → orderId=1030657...2618028, orderStatus=待支付 (status=10)
cancel-order  → {"cancelResult": true}
query-order   → orderStatus=订单已取消 (status=60)
```

三方金额一致：**求解器预测 = calculate-price = 订单 totalAmount = ¥23.80**。  
订单已撤销、未支付、无扣费。

## 六、怎么保证"真的对"

光"跑通了"不算数。项目的验证纪律是：

| 手段           | 结果                    |
| ------------ | --------------------- |
| 单元测试         | **64 项全绿**            |
| DP vs 穷举随机差分 | **120 组实例结果完全一致**     |
| 变异验证         | 故意注入 4 类缺陷，测试**全部捕获** |

"变异验证"是什么意思？就是**故意把代码改错，看测试会不会红**。  
如果改错了测试还绿，说明测试是摆设。

举个真实例子：我把名称匹配里的「块」字误当成容器词之后，  
`麦乐鸡4块` 立刻被错配成 `麦乐鸡5块` —— 179 kcal 和 223 kcal 差了一大截。  
测试当场报 FAIL。这才叫"边界真被守住了"。

## 七、怎么用

零第三方依赖，Python 3.10+ 直接跑：

```bash
# 1. 配置 Token（申请地址 https://open.mcd.cn/mcp）
export MCD_MCP_TOKEN=你的Token          # Windows 用 SetEnvironmentVariable 持久化

# 2. 按城市发现真实门店（不需要账号配置）
python -m mcd_meal_optimizer stores --city 上海

# 3. 核心：求解 + 真实算价复核
python -m mcd_meal_optimizer plan --city 上海 \
    --kcal-min 550 --kcal-max 800 --protein 30 --budget 40 --price-check
```

仓库里还附了一家门店的**完整真实快照**（121 项），不联网也能跑出同样结果。
